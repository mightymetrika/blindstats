CURRENT PRODUCT / SCIENTIFIC MODEL
----------------------------------
Study is the durable research container.

Blinding is the first research-specific workflow/module inside a Study.

Long-term product direction:
  Study = durable shell/container
  research workflows = modular apps inside the Study
  possible future direction = Research Management System (RMS)

Do NOT build broad RMS infrastructure before researcher feedback.

Persistent blinding workflow states:

  setup
    ↓
  blinded
    ↓
  unblinding_authorized
    ↓
  unblinded

AnalysisLock is a durable artifact/event, not a universal workflow state.
Multiple locks are supported.

IMPORTANT:
An AnalysisLock is recommended and is the default governance setting, but it is
not universally required. If the active immutable Plan explicitly sets:

  require_analysis_lock = false

the workflow can now proceed end-to-end without an AnalysisLock.

Core governance distinction remains:

  Request != Authorization != Exposure

Browser-local artifact schema remains:
  0.3


TWO-PARTY ANALYST BLINDING MODEL
--------------------------------
Blinding custodian / project lead:
  - has source/unblinded dataset
  - configures and activates Blinding plan
  - creates blinded package locally
  - retains unblinding secret
  - sends blinded dataset externally to analyst
  - later authorizes independent unblinding request
  - sends saved secret externally after authorization

Blinded analyst:
  - receives blinded dataset externally
  - analyzes while blinded
  - usually registers AnalysisLock when required by the Plan
  - requests unblinding
  - cannot authorize own independent request
  - receives secret only after authorization
  - locally verifies/decrypts mapping
  - downloads final unblinding receipt
  - registers safe completion metadata

Current external handoffs are intentional.
blindstats does NOT currently store/transfer:
  - source dataset contents
  - blinded dataset contents
  - substantive analysis artifact contents
  - plaintext unblinding secret
  - plaintext mapping
  - final unblinding receipt text

Persistent server records contain:
  - authenticated Study/membership/capability data
  - immutable Plan version
  - workflow state
  - exact public receipt
  - exact AnalysisLock receipt when one exists
  - safe artifact hashes/metadata
  - request / authorization / completion records
  - database registration timestamps

LATEST FIX: OPTIONAL ANALYSIS LOCK NOW WORKS END TO END
------------------------------------------------------
Problem discovered during documentation refresh:

  request_unblinding() already honored the active Plan's
  require_analysis_lock setting.

  authorize_unblinding() also honored that setting.

BUT:

  register_unblinding_completion() still unconditionally required an
  AnalysisLock-bound request and AnalysisLock metadata.

Therefore the old behavior was inconsistent:

  require_analysis_lock = false

could:
  - request without a lock
  - authorize without a lock

but could NOT:
  - persistently register completion without a lock

This mismatch is now fixed.

Commit:
  6cd8e7a Support unblinding completion without analysis lock

Migration:
  supabase/migrations/
  20261002223000_allow_unblinding_completion_without_lock.sql


DATABASE FIX DETAILS
--------------------
The new migration:

  1. makes AnalysisLock-specific columns nullable in
     public.unblinding_completions:

       analysis_lock_id
       analysis_lock_receipt_sha256
       analysis_artifact_filename
       analysis_artifact_sha256
       analysis_artifact_byte_length

  2. adds a consistency constraint so those fields must be:

       all NULL
       OR
       all populated

  3. replaces register_unblinding_completion() so completion follows the
     active immutable Plan and the actual request:

       - if the request is bound to an AnalysisLock:
           preserve the existing strong AnalysisLock chain validation

       - if the request has no AnalysisLock:
           allow completion only when the active Plan does not require one

  4. continues to verify:
       - workflow
       - Study
       - active Plan
       - registered transformation
       - request
       - authorization
       - transformation ID
       - selected column
       - source hash
       - public receipt hash
       - blinded artifact hash
       - safe receipt fields

  5. still does NOT receive/store:
       - plaintext secret
       - plaintext released mapping
       - final unblinding receipt text

  6. still atomically transitions:

       unblinding_authorized -> unblinded

IMPORTANT:
The previous deployed migration was not edited.
This was implemented as a NEW migration.


BROWSER / ARTIFACT FIX DETAILS
------------------------------
The browser-local schema 0.3 unblinding receipt now supports a legitimate
no-AnalysisLock path.

When no lock is used:

  lockId = null
  analysisLockReceiptSha256 = null
  analysisArtifact = null

The receipt still includes:
  - transformation ID
  - selected column
  - source artifact SHA-256
  - public blinding receipt SHA-256
  - blinded artifact SHA-256
  - unblinding secret SHA-256
  - released mapping

The persistent UnblindingWorkspace now:
  - uses the registered exact public receipt
  - does not require an AnalysisLock receipt when the request intentionally has no lock
  - still requires the locally supplied secret
  - locally verifies/decrypts the mapping
  - allows the final receipt to be downloaded
  - registers only safe completion metadata

Standalone file-mediated unblinding behavior remains strict and unchanged:
  - public receipt
  - secret
  - AnalysisLock receipt
are still required in standalone mode.
